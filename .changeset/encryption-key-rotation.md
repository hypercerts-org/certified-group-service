Operators can now rotate `ENCRYPTION_KEY` without needing to read the current key.

**Affects:** Operators

**Operators:**

- New optional env var `ENCRYPTION_KEY_NEXT`: 64 hex characters (32 bytes) that must differ from `ENCRYPTION_KEY`, compared case-insensitively. Setting it equal to `ENCRYPTION_KEY` fails startup with `ENCRYPTION_KEY_NEXT must differ from ENCRYPTION_KEY. If rotation is complete, remove ENCRYPTION_KEY_NEXT.` With it unset, the only change is the startup check below.
- When it is set, startup re-encrypts every stored app password and recovery key from `ENCRYPTION_KEY` to `ENCRYPTION_KEY_NEXT` in a single transaction before the server listens, then logs `Encryption key rotation complete` at `warn` with `groups`, `rekeyed` and `alreadyCurrent` counts. From then on `ENCRYPTION_KEY_NEXT` is used for everything, including groups registered or imported afterwards. Values already under the new key are skipped, so a restart with it still set changes nothing.
- To rotate: set `ENCRYPTION_KEY_NEXT` to a new key and redeploy, check the log line, then set `ENCRYPTION_KEY` to the same value, remove `ENCRYPTION_KEY_NEXT`, and redeploy. You never need to view the current key, so this works with sealed Railway variables. Back up the volume first. Once the re-key has committed (the `Encryption key rotation complete` log line) the old key can no longer read the stored values, so do not roll back to an earlier build or restore the old `ENCRYPTION_KEY`. The full runbook is in `docs/deployment.md#rotating-encryption_key`.
- If any stored value decrypts under neither key, startup fails with a `RekeyError` that names the group DID and column, for example `Cannot decrypt groups.encrypted_app_password for did:plc:abc with ENCRYPTION_KEY or ENCRYPTION_KEY_NEXT. No rows were changed. Check that ENCRYPTION_KEY is the key the data was written with.` The stored credentials are untouched.
- With `ENCRYPTION_KEY_NEXT` unset, startup now fails with `ENCRYPTION_KEY cannot decrypt any of the stored group app passwords (0 of 12 readable), so no group could log in to its PDS. If you just finished a key rotation, ENCRYPTION_KEY must hold the value that was ENCRYPTION_KEY_NEXT. Otherwise check that it is the key the data was written with. See docs/deployment.md#rotating-encryption_key.` when there are stored app passwords and `ENCRYPTION_KEY` can decrypt none of them. This catches a cut-over that left `ENCRYPTION_KEY` at the old or a mistyped value, which would otherwise start, pass its healthcheck, and then fail each group's first PDS login. An empty database passes, and one unreadable row among readable ones does not block startup. A database where no app password is readable used to start and fail per group; it now refuses to start. To recover from a failed cut-over, put `ENCRYPTION_KEY_NEXT=<new key>` back, leave `ENCRYPTION_KEY` as it is, and redeploy. If the key the stored credentials are encrypted with no longer exists anywhere, they cannot be recovered: restore the backup you took before the rotation if you still have the old `ENCRYPTION_KEY` it was encrypted under. Otherwise each group has to be reset and onboarded again, and there is no supported procedure for that yet.
- Rotating the key does not protect credentials an attacker has already decrypted. If both the old key and a copy of the data were exposed, the groups' app passwords and recovery keys must be replaced as well, which this change does not do.
